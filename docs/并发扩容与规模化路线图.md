# 并发扩容与规模化路线图

面向：约 50 人试点 → 500 / 5,000 / 20,000 同时在线（有预算时的工程路径）。  
原则：**先稳现有功能，再分层加「全局调度」；不把业务算力永久绑在浏览器里。**

---

## 当前形态（基线）

| 层 | 职责 |
|----|------|
| 浏览器 / Electron | UI、IndexedDB、多数 AI/背调/队列泵 |
| Vercel `api/*` | 上游代理（模型 / 检索 / 邮件 / 生图·3D） |
| Supabase | CRM / 历史 / 配置 / 作业队列同步 |

瓶颈不在「页面能不能打开」，而在：**共享上游配额、无全局作业上限、同 workspace 写合并、Serverless 长挂。**

---

## Phase 1（已落地，兼容现网）

目标：在**不改业务功能语义**的前提下，扛住「约 50 人同时登录 + 错峰重任务」。

| 项 | 做法 | 关键 |
|----|------|------|
| API 代理限流 | `api/_firewall.ts` → 各 `api/*.ts`；优先按 Key 指纹，避免公司 NAT 误伤 | 可用 `API_RL_MAX_QWEN` 等环境变量调大/调小 |
| 负载治理 | `services/loadGovernor.ts`：跨标签登记重任务；高峰把 `both` 收成单路 | 也可 `VITE_LOAD_CAP_SINGLE_ENGINE=1` 强制单引擎 |
| 限流共享 | `rateLimitGate` + 跨页 `trade_scout_shared_cooldown_until` | 减轻 429 后惊群 |
| Key 耗尽协调 | 本机池 + 可选表 `key_quota_state`（`scripts/supabase-key-quota-state.sql`） | 未建表则静默跳过 |
| 云同步 | `syncAllWorkspaceData` 同页串行合并 + 上传前抖动 | 登录拉/推逻辑不变 |
| 队列 | 深挖 / 补全 / 设计信号等泵前 `waitForLocalAiSlot`；邮件搜高峰降并发 | 空闲行为与原来接近 |

**运维建议（50 人）：**

1. 配置独立 `VITE_WORKSPACE_ID`（长随机串），并执行 `scripts/supabase-rls-harden.sql`。  
2. （可选）执行 `scripts/supabase-key-quota-state.sql`。  
3. Vercel 升到足够并发的套餐；密钥池按「峰值同时重任务数 × 单任务调用次数」备量。  
4. 高峰演示日可临时打开强制单引擎。

Phase 1 **不能**保证 50 人同时全员狂跑批量背调/生图——那需要 Phase 2 的全局队列。

---

## Phase 2 — 约 500 同时在线（建议预算重心）

**产品定义：** 500 人可登录、看 CRM、轻度检索；同时进行的「重 AI 作业」全局上限约 30–80（可调），其余排队可见进度。

| 工作 | 说明 |
|------|------|
| 真·租户 | Supabase Auth（或自建 SSO）+ `org_id` / `dept_id`；弃用共享 `default` |
| 服务端作业队列 | 背调 / 批量搜邮 / 生图入队；Worker（Cloud Run / Fly / 自建）拉取；浏览器只提交与订阅状态 |
| 全局 Key / 限流 | Redis（或 Upstash）存 RPM、耗尽、冷却；代理层强制；禁止仅靠各端 localStorage |
| 密钥出浏览器 | 上游 Key 仅服务端；前端只带会话 JWT |
| 同步改增量 | CRM/历史按 `updated_at` 增量；冲突用行版本；禁止全员全量 upsert |
| 可观测 | 队列深度、429 率、P95 代理时延、按租户配额看板 |

**预算粗指引：** 应用托管 + Redis + Worker + 观测 ≈ 中小；**模型/检索调用费**随活跃重任务线性涨，通常大于基建。

## Phase 3 — 约 5,000 同时在线

| 工作 | 说明 |
|------|------|
| 读写分离 | CRM 列表走只读副本 / 缓存；写走主库 |
| 对象存储 | 报告附件、创意素材上对象存储，库内只存元数据 |
| 边缘静态 | 前端 CDN；API 按区域就近 |
| 分片租户 | 大客户独立 schema 或独立 Supabase 项目 |
| 配额产品化 | 套餐：并发作业数、日调用量、部门池；超限排队或降级 |
| 异步一切长任务 | 禁止 300s 同步挂死；提交 → 轮询/WebSocket |

此阶段浏览器侧队列应降为「本机草稿/离线」，**云端队列为唯一真相。**

---

## Phase 4 — 约 20,000 同时在线

| 工作 | 说明 |
|------|------|
| 多区域 | 就近接入 + 租户数据驻留合规 |
| 消息总线 | 作业事件、通知、审计日志 |
| 专用推理网关 | 统一路由多模型供应商、熔断、缓存语义化结果 |
| 会话与连接 | 有状态通知用托管 WebSocket / SSE；无状态 API 水平扩展 |
| 安全与合规 | 审计、脱敏、密钥轮换、渗透与 SOC 流程 |
| 组织架构 | 平台组 / 数据组 / 模型成本组；SRE on-call |

**20,000「同时在线」≠ 20,000「同时跑背调」。**  
容量规划应拆成：在线会话、QPS、重作业并发、存储 IOPS 四条曲线分别扩。

---

## 能力对照（务实）

| 规模 | 仅配置/密钥加量 | + Phase1 | + 全局队列与租户（Phase2+） |
|------|-----------------|----------|------------------------------|
| 50 人轻用 | 勉强 | **推荐** | 过度 |
| 50 人全员重任务 | 否 | 部分排队/降级 | 需要 |
| 500 | 否 | 不足 | **需要** |
| 5,000 / 20,000 | 否 | 否 | 需要 Phase3/4 |

---

## 有奖金时的投入顺序（ROI）

1. **模型与检索配额 + 密钥池**（立刻提升并行上限）  
2. **服务端作业队列 + Redis 限流**（从「能用」到「可控」）  
3. **Auth 多租户 + 增量同步**（数据不错乱）  
4. **观测与成本看板**（避免钱烧在盲打 429）  
5. **再**考虑多区域与中台化
